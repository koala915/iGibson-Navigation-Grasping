# v23 demo 有限恢復與降級

## 項目與目的

| 項目 | 目的與實際行為 |
|---|---|
| Serial 防卡死 | 單一持有者、單一接收執行緒；read 0.1 s、write 0.2 s、取寫入鎖 0.2 s。接收例外退避後繼續唯讀接收，不重開埠、不重播命令。 |
| 寫入故障保留 | 驅動即使吞掉例外，上層仍知道寫入失敗，不把軟體零命令當成已成功停輪。写入故障保持鎖定，不能靠下一次成功讀取清除。 |
| 真實回傳新鮮度 | 驗證封包長度／checksum；底盤／odom 使用 0x0A 速度回報時間，伺服回覆不能讓停止更新的里程計看起來新鮮。 |
| 獨立健康入口 | `/tmp/grasp_health.sock` 只允許 health，手臂動作佔用主命令迴圈時仍可診斷；手臂命令例外回覆失敗而非退出服務。 |
| 等待與有限修復 | 每個步驟前後最多等待 30 s，故障後連續 3 筆正常才接續。每個允許服務最多修復 2 次、全域冷卻 10 s。 |
| 常駐監督 | 每秒覆寫 `/tmp/v23_monitor.json`；不載入模型、不開相機／Serial。任務執行期間不搶修；Serial 不健康時保留診斷。 |
| 導航短暫停等 | demo 的短直線可停輪等待最多合計 3 s，連續 3 筆新鮮且靜止資料後續走，保留原 odom 起點／距離目標／原煞車閘。無进度、錯誤 frame、odom 跳變仍停止，不以加速解決卡輪。 |
| 檢查點 | 動作前記錄 inflight，動作完成且實際狀態通過後才記錄完成。人工 `--resume` 只接續完成點；同開機、同服務 PID、同計畫且姿態／載物一致才接受。 |
| 功能降級 | 相機等故障耗盡等待後，控制仍健康可嘗試一次 stow 並驗證，進入 parked；部分導航／未知手臂結果進入 diagnostics，不投放、不重播。 |
| RAM 保護 | 不足 1024 MB 暫停新步驟與修復；導航低於 768 MB 停止自己的子程序。監督器只保留一份狀態與固定計數，不累积 scan／影像。 |

## 執行

```bash
# 常駐被動監督（不啟動展示／不送移動）
~/grasp_venv/bin/python3 grasp/v23/demo.py monitor --restart-owner
# 正常 demo 自動使用等待、有限修復、降級及檢查點
~/grasp_venv/bin/python3 grasp/v23/demo.py --plan grasp/v23/demo_grasp.json --execute
# 明確接續已驗證完成點；未知結果或服務重啟會拒絕
~/grasp_venv/bin/python3 grasp/v23/demo.py --plan grasp/v23/demo_grasp.json --execute --resume
```

`deploy/systemd/v23-demo-monitor.service` 提供開機監督單元，須部署全部相依檔並比對
遠端校正／原始檔後才能安裝啟用；不自動啟動 demo。
只有 grasp-vision、x3plus-g2-lidar、x3plus-g2-rosbridge 可有限重啟，且要求
唯一 Serial owner、足夠 RAM、已驗證 idle/travel、取得 maintenance 鎖。
一般感測修復失敗／逾時保留鎖，不自動執行 home/release。
監督器以 demo flock 避免與任務修復競爭。

## 難以恢復時的升級重啟

`--restart-owner`：Serial 故障持續 15 s，可升級重啟 grasp-service。
前提為新版 health API、唯一 owner、RAM ≥1024 MB、軟體零速、無 TCP client、
手臂 idle/travel、空夾爪且沒有該 owner 的未知動作 checkpoint。
服務以 `restart-lock` 原子鎖住手臂／底盤入口，故障自行恢復或已有新動作時拒絕重啟。
監督器先記錄 `/tmp/v23_restart_budget.json` 與 `/tmp/v23_restart_no_motion.json`，
再透過 systemd 停舊服務／啟新服務，不另開 Serial；逾時也消耗預算。
每次開機最多一次監督器主動重啟，監督器自身重啟不會清掉此預算。
既有 systemd on-failure 與 StartLimit 仍可能重試啟動；同一次開機的 no-motion marker
會套用於這些啟動，防止再次歸位／張爪。

恢復啟動只送零輪命令／讀取編碼器，不自動 home/stow/release。
巡航姿態、張爪角度與新鮮速度回報未驗證時，TCP 不開啟、手臂命令拒絕，健康 socket 保留。
marker 僅適用本次開機；損壞時保守使用唯讀啟動。
重啟會使服務 PID 與 odom 原點改變，因此原 checkpoint 不自動接續，導航需重新驗證／定位。
health 完全無法取得、仍在動作、載物或動作結果未知時，不強制殺掉服務，保留診斷。

## 測試與部署界線

故障注入涵蓋暫時讀取例外、雜訊／checksum、寫入故障與鎖逾時、最多兩次修復、
連續正常閘、檢查點身分／inflight 拒絕、未知結果不重播、相機失敗降級、導航停等。
本機 pytest 與導航／controller／bus／floor／travel／odom／UI 回歸證據在
`v23_recovery_20261007/`；Linux 暫存測試通過 startup 13 項、獨立 socket 與
實機安裝版 Rosmaster 的速度封包解析（使用 fake Serial，沒有硬體寫入）。
Linux venv 未安裝 pytest，完整新 pytest 未在 Jetson 執行；CI 已加入該套件。

新版仍未覆寫正式部署或啟用監督單元，未發實機動作，USB 問題不處理。
尚需正式服務重启、冷開機與實車故障注入驗收；不能保證核心／硬體故障時仍能送停車封包。
控制板端 watchdog 與完整自主導航／定點夾取以外的替代展示尚未完成。
降級不是「原任務成功」，狀態會明確回傳 degraded／mode／reason。
