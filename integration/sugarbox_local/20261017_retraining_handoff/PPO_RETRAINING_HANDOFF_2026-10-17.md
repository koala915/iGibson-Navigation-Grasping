## 3. 原本 PPO 的背景

現用模型名為 `doorway_ft_final.zip`。2026-10-12 曾比對我實際載入檔與部署 repo 模型，兩者 SHA256 同為：

```text
af5e9e1d5ce0115de8b4bbb321873c6a99686c82c0c69d060f881bbe97b64f35
```

舊訓練資料記載：`Rs_int` 場景、55 維觀測、2 維連續動作、約 6 Hz、48 束前方 ±90° LiDAR；觀測包含目標距離、方向 sin/cos、平面速率、角速度、上一筆原始動作與 LiDAR。動作是前後油門與旋轉，不含獨立側移。

doorway 模型是既有模型再續訓約 80,000 步，混合穿門、單目標與 waypoint 任務，不是專門為我的 Sugarbox 接近、鏡頭交接或自動夾取訓練。

舊設定值得修正或驗證的項目：

- 已有 `-0.05 * norm(action - prev_action)` 平滑懲罰，但不能據此宣稱抽動已解決。
- 障礙近、油門小時，轉向幅度可得到正獎勵，不區分左右；反覆轉向可能受益，但這不是已證實的實車故障根因。
- 設定 `obstacle_close_dist=0.25`，模擬射線輸出下限卻是 0.33 m，這項額外近障懲罰不會觸發。
- 同理，`collision_threshold=0.22` 的射線碰撞分支不會觸發；仍有物理接觸碰撞判定，不可誤寫成完全沒有碰撞懲罰。
- 舊訓練有 2-step action delay、stall assist、近障調速；它們是動作處理，不是 reward。與目前實機是否相符要逐項核對。
- 直接靠近目標、一直對準目標的獎勵，可能與必要繞路互相拉扯。

## 4. 本機實機模式的關鍵差異

2026-10-17 唯讀核對本機原始碼後，10/12 的錄影入口仍設定：

```text
SUGARBOX_TRAINING_CONTRACT=1
SUGARBOX_PPO_ONLY=0
SUGARBOX_TARGET_INITIAL_ONLY=1
SUGARBOX_FOOTPRINT_GUARD=0
SUGARBOX_ARM_HANDOFF=1
CONTRACT_ACTION_DELAY_STEPS=0
```

但 `PPO_ONLY_DIAGNOSTIC = PPO_ONLY旗標 OR TRAINING_CONTRACT_DIAGNOSTIC`，所以這個模式仍跳過 `anti_jitter.apply()`，保留 0.45 m 診斷停車條件。畫面列印過濾器參數，不代表真的執行該過濾器。

因此，**不要把上次錄影模式當成「原有完整過濾器已在執行」或「過濾器已經驗證有效」的證據**。

本機有一份候選換向邏輯：近障進入 0.45 m、離開 0.55 m、有效轉速門檻 0.12 rad/s、新方向連續 2 tick 才換向；等待時輸出零轉速，不沿舊方向反向執行新指令。它可能引入停頓，必須單獨評估，不能直接認定是最後定案。

目前實機測試上限為前進 0.15 m/s、後退 0.08 m/s、旋轉 0.78 rad/s，policy LiDAR scale 為 1.0。這些是目前測試值，不是必然最佳的訓練設定。未量測前，不擅自提高速度或恢復人工兩步延遲；真實通訊與馬達延遲仍需建模。

10/12 第一輪：使用者回報碰撞，未交接，最後記憶距離 0.436 m，停在診斷距離限制；第二輪同版確實觸發 exit 42，停車後回手臂循線姿態並預覽。第二輪沒有足夠資訊可宣稱完全無碰撞；兩輪均未自動夾取。

## 5. 要建立的訓練與部署契約

```text
目標 + 感測資料 + 車速 + 過濾器狀態
  -> PPO 原始動作 a_raw
  -> 動作映射與共用過濾器
  -> 實際施加指令 u_applied
  -> 模擬移動
  -> 任務獎罰 + 原始動作抖動成本 + 介入成本
```

- 從選定實機過濾邏輯抽出可離線測試、可序列化參數、可 reset 的共用核心。不要直接 import 帶 YOLO、GUI、網路或硬體副作用的巨大實機主程式進訓練。
- 最小候選：左右換向確認、小幅指令雜訊處理、必要的速度變化限制。後兩項及各門檻仍需設計，不可聲稱目前都已存在或啟用。
- 保持必要換向能力；不盲目鎖住錯誤方向，不讓平滑限制延遲急停。
- 卡死倒退、目標搜尋、鏡頭交接、到位判斷不全部塞入這一層。若日後把有狀態 recovery 納入訓練，也須明確定義狀態與一致實作。
- 觀測至少要評估加入上一筆實際施加指令、轉向保持狀態、待確認方向及計數；若有 slew、延遲緩衝或 recovery 計時器，也要納入足夠狀態或歷史。
- 新觀測布局必須版本化，重新配對模型與 VecNormalize。維度改變不能直接 `PPO.load` 舊權重宣稱可續訓；從零訓練或經驗證的權重移植另行比較。
- PPO rollout 的 action/log-prob 仍對應它真正採樣的 `a_raw`。過濾器是環境動態的一部分，不把 `u_applied` 冒充原始採樣動作。

## 6. 幾何、感測與碰撞

使用者提供的近似實測：車寬 0.25 m、長 0.32 m；LiDAR 約在車體中心前方 0.09 m；視覺目標距離以前緣為基準，換到中心約加 0.135 m。

**前緣 0.135 m 與半車長 0.16 m 不相等，需核對各自參考點、有效碰撞外形與突出物，不能硬當作同一個量。**

- 所有目標與 LiDAR 點轉到同一車體座標。先將射線轉成 XY，再做平移/旋轉；不是每束距離一律加減 9 cm。
- 前方有效 LiDAR 覆蓋維持 ±90°；不要讓模擬偷偷提供實車看不到的後方觀測。
- LiDAR 角度方向與軸向以當前底層與實測證據為準。歷史上有底層重寫，不能根據舊說法再次猜左右或前後翻轉。
- 實際碰撞依真實外形建模，淨空依車身邊界與轉彎掃掠範圍計算，安全裕度獨立列出。候選裕度 0.08 m，尚未驗證。
- 不把 0.33 m 的射線起始半徑誤當成已完成車身膨脹；要檢查盲區、下限、collision geometry 與 reward 計算是否一致。
- raw 接觸/淨空判定不能依賴已被 clip 到較大下限的 policy rays。檢查 LiDAR 高度及低矮障礙不可見的問題。
- 模擬可用全場景幾何判定真碰撞與訓練成本，但不可把實車沒有的地圖/後方資訊偷偷放進 policy 觀測。
- 保留既有 odom 校正不動；需要建模的是實車誤差，不是用新 reward 掩蓋座標或感測錯誤。

## 7. 獎罰方案：共識與待調參數

以下是實驗起始提案，不是已驗證最佳值；先記錄各分項量級，不一次同時大改所有項目。

| 項目 | 初始提案／要求 |
| --- | --- |
| 成功 | 安全到達導航交接區並停穩，一次 +300；交接區、速度與停留條件需另行定義及驗證 |
| 碰撞 | 真實車身接觸障礙，-300 並結束；包括側邊擦撞 |
| 進展 | 獎勵有效往導航終點進展，容許避障必要繞路；不要沿用強烈直線接近與強制對準壓力而未比較 |
| 近障 | 車身淨空不足漸進扣分；先試 8 cm 裕度、每步最多約 -0.5，需依控制頻率與實測調整 |
| 原始抖動 | 對歸一化 `a_raw` 的相鄰變化加小成本，候選係數 -0.1；L1/L2/平方形式需明確固定 |
| 反覆換向 | 對有效幅度以上、短時間無效反轉加小成本；不全面禁止合理倒退/換邊，與動作變化成本分項驗證 |
| 過濾介入 | 對不必要修正的幅度/頻率加小成本，係數待標定；防止原始指令仍亂跳、全部靠過濾器承擔 |
| 時間 | 每步 -0.05 起步；改控制頻率時應按時間重新換算 |
| 單純轉動 | 先取消舊「近障低油門轉向就加分」項目 |
| 長期停滯 | 第一版不額外加大懲罰，先靠時間成本與失敗統計；避免逼迫車子為了動而撞 |

介入成本要比較同座標、同單位且合理歸一化的「提議 twist」和「過濾 twist」，不能直接拿 throttle 與 m/s 相減。分開記錄軟過濾、硬保護、人工急停與感測故障；不能為降低介入成本而取消保護或放行危險動作。

可研究用模擬地圖的可行路徑剩餘距離做進展 shaping；這不是先決條件，也不等於讓局部 PPO 變成全域規劃器。若用 potential-based shaping，需配合 gamma、終止狀態、timeout bootstrap 及 waypoint 切換，避免刷分或跨目標跳變。不要只把直線 reward 換掉卻未處理這些細節。

## 8. 視覺、導航成功與夾取要分開

長期流程：PPO 避障接近 -> 停車交接手臂鏡頭 -> 影像對準/近距離接近 -> 確認可夾位置 -> 夾取。

接近與影像對準期間維持同一巡航姿態，不再做 S2 三段式或畫面到底部時自動下看。錄影模式只切相機預覽，不夾取；未來真正的夾取動作另行設計及確認，不在本次重訓/固定姿態變更中啟動。

- 導航終點應對應可交接的區域，不是 Sugarbox 實體中心；數值尚未校準，不填假數據。
- 不沿用 0.45 m 診斷停止當成功，也不能將「目標消失」「無碰撞但卡住」當成功。
- 交接判斷與 target-search 的避障淨空 gate 要分開設計；目前共用 gate 可能讓近目標交接被擋住。
- 深度先考慮改善視覺目標距離；第一階段不把深度影像直接加入 PPO 網路。
- 保留目標記憶的需求；目標重新偵測的資料關聯與濾波另列工作，不在這次導航重訓中暗改。
- 手臂最終可夾位置仍未校準。不可假設目前已完成自動夾取，也不可自動啟動實機驗證。

## 9. 實作、測試與比較順序

1. 盤點組員環境：Python、iGibson、場景資產、SB3/PyTorch、目前訓練 commit、舊權重及 VecNormalize。能 import iGibson 不等於能載入 `Rs_int` 跑 episode；不要先升級原本能用的環境。
2. 凍結舊 baseline 與原始評估輸出；保存 manifest、hash、設定與 random seeds。
3. 選定最小過濾器，寫純邏輯測試：小雜訊、左右反覆、合理換向、清空/reset、不同 dt、急停立即生效、感測無效與保護狀態。
4. 建立 train/deploy 一致性測試：同感測、原始動作與過濾器狀態，逐步產生同一指令；每回合 reset，不洩漏前回合狀態。
5. 固定幾何、動作響應與新 observation/action/filter 契約，再分項加入 reward；確認各分項真的會觸發。
6. 課程由單一障礙、偏左/偏右障礙，到窄通道、多障礙與不同起點。訓練與測試分開，不只在同一扇門證明泛化。
7. 對照舊模型原流程、舊模型加選定過濾器、新模型加同一過濾器。舊模型維持自己的原始 observation adapter；不要將新維度直接餵舊模型。統一外部任務/幾何條件，並明確記錄無法完全一致的動作契約差異。
8. 用固定評估情境及多批不同 seeds，分開比較濾波、獎勵和感測改動；不要只挑一條成功影片或最高訓練總分。
9. 模擬通過後另提出低速、有人監督的實機驗證計畫，得到明確同意才執行。不要為診斷而在實車關掉保護。

必要日誌：timestamp/dt、target、raw/policy LiDAR 與有效性、車體狀態、`a_raw`、映射後提議 twist、過濾後/實際施加 twist、過濾器狀態及介入理由、reward 分項、碰撞/成功/timeout 原因、模型和設定識別。

評估至少報告：成功率、碰撞率、最小車身淨空、完成時間、停滯時間、原始與實際動作各自的總變化/反轉次數、軟過濾及硬保護介入率。尚未訂正式通過門檻，不可自行宣稱某次數值已達驗收標準。

## 10. 成功定義與組員 Codex 第一個回覆

**車子不抖，但 PPO 原始指令仍不停反轉：只是被過濾器壓住，未解決策略問題。指令平順但卡住、撞到或到不了：仍是失敗。**

我們要的是：原始指令較穩定、過濾介入減少、碰撞減少、保留適當淨空，而且能持續避障到達，不是停車就當安全成功。

請先回覆：實際訓練環境/commit 與本文件的差異、可重用的程式、過濾器最小方案、新觀測布局、舊權重相容策略、reward 分項與驗證方式、預計的檔案修改範圍及實驗順序。先不要直接訓練、改實機或合併流程。
